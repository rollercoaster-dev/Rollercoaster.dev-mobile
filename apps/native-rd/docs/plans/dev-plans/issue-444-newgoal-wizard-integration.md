## Discovery Log

- [2026-08-07] **Step ordering changed so every commit stays green.** The plan's Step 1 replaced the `newGoal` namespace wholesale, which breaks `namespace-convention.test.ts` while `NewGoalModal` (and its test) still reference `newGoal:title` / `fields.*` / `cta.*`. Step 1 was made purely _additive_ instead — the wizard copy lands alongside the old keys — and the now-dead old keys are deleted in Step 3 together with the screen that used them. Three commits, same shape as the plan, all three green.
- [2026-08-07] **Container split into three files.** `NewGoalScreen.tsx` as a single file came to 446 lines and tripped `local/file-size-limit` (max 300). Extracted `useNewGoalSteps.ts` (step-list state + the eleven build-list reducers + the step-2 derivation) and `newGoalWizardCopy.ts` (the `t()` lookup table); the container is down to 167 lines and owns only navigation, step history and the persist batch. Both extractions are single-responsibility, not speculative abstraction.
- [2026-08-07] **`applyReparent` is not re-exported from `components/EditGoalView/index.ts`.** Imported from `../../components/EditGoalView/applyReparent` directly, exactly as `NewGoalWizard.stories.tsx` does. Not widened here — that would be an unrelated barrel change.
- [2026-08-07] **`NewGoalWizard`'s `STEP_ORDER` isn't exported**, so the container carries its own `NEXT_STEP` map over the exported `NewGoalWizardStep` union. Exhaustive by type, so a step added to the union fails type-check here rather than silently dead-ending.
- [2026-08-07] **`runEvoluMutation` can't drive the persist batch.** It returns `boolean`, and the batch needs each insert's `value.id` to feed the next call (`goalId` → `createStep` → `parentStepId` → `createSubStep`). The batch checks `.ok` per call inside one `try`/`catch` instead — both of Evolu's failure modes covered, same as the helper, no new helper minted.
- [2026-08-07] **`errors.createFailed` became `createFailedTitle` + `createFailedMessage`.** The failure surface here is an `Alert.alert`, which needs both, following `editGoal.json`'s `deleteGoalTitle`/`deleteGoalMessage` pair. The message deliberately does _not_ claim "nothing was saved" — a mid-batch failure can leave earlier rows in place (no rollback, per Not in Scope).
- [2026-08-07] **Zero-step goals are fine.** Quick-add → Ready → Start Working creates a goal with no steps. `FocusModeScreen` already renders `NoActionableBody` with `stepCount={0}`, so no gate was added and the case is covered by a test.
- [2026-08-07] **i18next's generated key union can't express plural lookups** (`newGoal:build.stepCount` exists only as `_one`/`_other`), which `tsconfig.test.json` catches. The test widens `i18n.t` once at the top rather than casting at ~20 call sites.
