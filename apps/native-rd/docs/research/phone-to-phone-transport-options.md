# Phone-to-Phone Transport Options — iOS ↔ Android Without Infrastructure

**Date:** 2026-09-21
**Status:** Research, not a decision
**Owner:** Joe

**Scope reference:** [Peer evidence spike](../../prototypes/peer-evidence-spike/README.md) (blocked by Wi-Fi client isolation on 2026-09-21), [Pear evaluation](./pear-p2p-evaluation.md), [Community learning vision](../vision/community-learning-and-peer-validation.md), [Minimal peer validation gaps](./2026-09-20-minimal-peer-validation.md)

**Target app:** Expo SDK 56 / React Native 0.85.3, iOS + Android, New Architecture (Nitro modules already in use).

---

## TL;DR

The requirement is: two people in the same room, one iPhone and one Android phone, no usable venue Wi-Fi, no user-visible hotspot setup, ideally no internet. Exchange a ~200-byte pairing token, move 0.5–10 MB of credential JSON + PNG + WAV, return a ~2 KB signed response.

1. **Bluetooth LE is the only radio that is cross-platform, infrastructure-free, and available to third-party apps on both OSes today.** It is slow: theoretical ceiling ~1.4 Mbit/s at LE 2M PHY with Data Length Extension, ~0.8 Mbit/s at 1M, ~0.39 Mbit/s with legacy 27-byte packets ([SIG timing analysis](https://www.bluetooth.com/blog/exploring-bluetooth-5-how-fast-can-it-be/)). At those ceilings 5 MiB takes 29 s / 52 s / 108 s. Real phone-to-phone rates are lower and **we have not measured them**; a working assumption of 150–800 kbit/s puts 5 MiB at **1–5 minutes**. Acceptable for a one-off in-person hand-over if the UI shows progress, not for anything larger.
2. **Wi-Fi Aware (NAN) is the standards-based high-bandwidth answer on paper** — Android API 26+, iOS 26+ on iPhone 12+ ([Apple](https://developer.apple.com/documentation/wifiaware)) — but iPhone ↔ Android pairing is **not demonstrated working** as of September 2026. Apple requires Wi-Fi Aware 4.0 with NAN Pairing ([ADG §56](https://developer.apple.com/accessories/Accessory-Design-Guidelines.pdf)); Android's `isAwarePairingSupported()` (API 34) is vendor-gated and mostly `false`; Apple DTS refers reporters to silicon vendors ([forum 790195](https://developer.apple.com/forums/thread/790195), [forum 801280](https://developer.apple.com/forums/thread/801280)). Treat as a 2027 candidate, not a 2026 transport.
3. **Android local-only hotspot + iOS programmatic join** is the one high-bandwidth path that works today with only OS prompts and no user setup: Android `WifiManager.startLocalOnlyHotspot()` (API 26, no internet on that network) hands the app an SSID/passphrase; iOS `NEHotspotConfigurationManager` (iOS 11, entitlement) joins it after a system approval prompt. This is exactly Google Nearby Connections' `WIFI_HOTSPOT` medium. It costs the iPhone its internet Wi-Fi for the session and needs a native module we would write.
4. **Everything else is single-ecosystem or infrastructure-bound:** Multipeer Connectivity (Apple only), Nearby Connections (iOS build supports Wi-Fi LAN only — blocked by client isolation), Wi-Fi Direct (no iOS API), Bluetooth Classic (iOS needs MFi), AirDrop/Quick Share (files only, no return channel, Pixel-only interop today).
5. **Recommendation:** pair over **QR code** (expo-camera, already in the app), transfer over **BLE** (GATT server/peripheral on one phone, L2CAP CoC upgrade where both sides support it), **opportunistically upgrade to the Android-hotspot path** for the media, and keep the **HyperDHT/internet route as the fallback when both phones have cellular**. Next spike: prove BLE peripheral + central across an iPhone and a Galaxy A16 with a measured 5 MiB transfer time.

## 3. Option-by-option

### 3.1 Bluetooth LE — GATT

**Platform support.**

- iOS: `CBPeripheralManager` (act as GATT server, advertise) since iOS 6; `CBCentralManager.connect` since iOS 5 ([CBPeripheralManager](https://developer.apple.com/documentation/corebluetooth/cbperipheralmanager), [connect](<https://developer.apple.com/documentation/corebluetooth/cbcentralmanager/connect(_:options:)>)). `NSBluetoothAlwaysUsageDescription` is required on iOS 13+ or the app crashes ([Core Bluetooth](https://developer.apple.com/documentation/corebluetooth), [key](https://developer.apple.com/documentation/bundleresources/information-property-list/nsbluetoothalwaysusagedescription)). Foreground advertising gets 28 bytes of payload plus 10 bytes of local name in the scan response; in background the local name is dropped and service UUIDs move to an overflow area only iOS scanners see ([startAdvertising](<https://developer.apple.com/documentation/corebluetooth/cbperipheralmanager/startadvertising(_:)>)). That last point matters: **an Android phone will not discover a backgrounded iPhone by service UUID.** Background operation needs the `bluetooth-peripheral` / `bluetooth-central` background modes ([CBPeripheralManager](https://developer.apple.com/documentation/corebluetooth/cbperipheralmanager), [scanForPeripherals](<https://developer.apple.com/documentation/corebluetooth/cbcentralmanager/scanforperipherals(withservices:options:)>)).
- Android: `BluetoothGattServer` since API 18 ([reference](https://developer.android.com/reference/android/bluetooth/BluetoothGattServer)); `BluetoothLeAdvertiser` since API 21 ([BluetoothAdapter](https://developer.android.com/reference/android/bluetooth/BluetoothAdapter)). Permissions on API 31+: `BLUETOOTH_SCAN` (with `android:usesPermissionFlags="neverForLocation"` if you can assert no location derivation), `BLUETOOTH_ADVERTISE`, `BLUETOOTH_CONNECT`; legacy `BLUETOOTH`/`BLUETOOTH_ADMIN`/`ACCESS_FINE_LOCATION` with `maxSdkVersion="30"` ([Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)).

**Packet size.** Default ATT MTU is 23 bytes (20 bytes of payload). Android `requestMtu` (API 21) negotiates larger; from Android 14 the stack always asks for 517 and ignores later requests, and the negotiated value is `min(517, remoteMtu)` ([requestMtu](<https://developer.android.com/reference/android/bluetooth/BluetoothGatt#requestMtu(int)>), [Android 14 behavior change](https://developer.android.com/about/versions/14/behavior-changes-all#mtu-set-to-517)). iOS negotiates MTU itself; `maximumWriteValueLength(for:)` (iOS 9) tells you the usable size per write type ([reference](<https://developer.apple.com/documentation/corebluetooth/cbperipheral/maximumwritevaluelength(for:)>)). Notifications from an iOS peripheral truncate to the central's `maximumUpdateValueLength` and `updateValue` returns `false` when the transmit queue is full — you must wait for `peripheralManagerIsReady(toUpdateSubscribers:)` ([updateValue](<https://developer.apple.com/documentation/corebluetooth/cbperipheralmanager/updatevalue(_:for:onsubscribedcentrals:)>)). Write-without-response exists on both sides ([iOS](https://developer.apple.com/documentation/corebluetooth/cbcharacteristicwritetype/withoutresponse), [Android `WRITE_TYPE_NO_RESPONSE`](https://developer.android.com/reference/android/bluetooth/BluetoothGattCharacteristic)).

**PHY.** Android exposes `setPreferredPhy(PHY_LE_2M…)` from API 26 as a recommendation the controller may ignore ([BluetoothGatt](https://developer.android.com/reference/android/bluetooth/BluetoothGatt)). iOS negotiates LE 2M transparently on iPhone 8 and later ([WWDC19 session 901](https://developer.apple.com/videos/play/wwdc2019/901/)). Apple's accessory guidelines constrain connection intervals to multiples of 15 ms with a 15 ms floor, and note some Apple devices offer 30 ms instead ([ADG §58.6](https://developer.apple.com/accessories/Accessory-Design-Guidelines.pdf)).

**Throughput.** The Bluetooth SIG's own timing analysis gives one full data packet plus empty acknowledgement per exchange: 27-byte payload at 1M ≈ 558 µs per 216 bits (≈ 0.39 Mbit/s); 251-byte payload (Data Length Extension, Core 4.2) at 1M ≈ 2 500 µs per 2 008 bits (≈ 0.80 Mbit/s); 251 bytes at 2M ≈ 1 400 µs (≈ 1.43 Mbit/s) ([SIG blog](https://www.bluetooth.com/blog/exploring-bluetooth-5-how-fast-can-it-be/)). Those are link-layer ceilings with the radio saturated; ATT/L2CAP headers, connection-event scheduling, phone controller policies (iOS especially) and coexistence with Wi-Fi all cut into them. **We do not have a measured iPhone ↔ Android number.** Working assumption for planning: 150–800 kbit/s → 5 MiB in roughly 1–5 minutes; the 2 KB return trip is sub-second. This is the main uncertainty of the whole document and the first thing the next spike must measure.

**Interop reality.** iOS ↔ Android GATT works; it is what every cross-platform BLE app does. Pitfalls are well-known and all solvable in code: iOS backgrounded advertising invisible to Android; MTU asymmetry (send in chunks sized by the smaller side); Android 14 MTU behaviour; flow control on notifications. No system pairing dialog appears for an unencrypted custom GATT service — encrypt at the app layer (we already have device P-256 keys).

For a symmetric app (either phone may host) the realistic plan is a small Nitro module wrapping `CBPeripheralManager` + `BluetoothGattServer` and (optionally) L2CAP, alongside `react-native-ble-manager` for the central role — or one module for both roles.

### 3.2 Bluetooth LE — L2CAP connection-oriented channels

- iOS: `CBPeripheralManager.publishL2CAPChannel(withEncryption:)` and `CBPeripheral.openL2CAPChannel(_:)` since iOS 11; the system assigns a dynamic PSM and "L2CAP channels aren't discoverable by themselves, so it's the app's responsibility to handle PSM discovery on the client" — i.e. publish the PSM in a GATT characteristic ([publishL2CAPChannel](<https://developer.apple.com/documentation/corebluetooth/cbperipheralmanager/publishl2capchannel(withencryption:)>), [openL2CAPChannel](<https://developer.apple.com/documentation/corebluetooth/cbperipheral/openl2capchannel(_:)>), [CBL2CAPChannel](https://developer.apple.com/documentation/corebluetooth/cbl2capchannel)). The channel is a pair of `NSStream`s.
- Android: `BluetoothAdapter.listenUsingL2capChannel()` / `listenUsingInsecureL2capChannel()` (dynamic PSM via `BluetoothServerSocket.getPsm()`) and `BluetoothDevice.createL2capChannel(psm)` / `createInsecureL2capChannel(psm)`, all API 29, "LE only" ([BluetoothAdapter](https://developer.android.com/reference/android/bluetooth/BluetoothAdapter), [BluetoothDevice](https://developer.android.com/reference/android/bluetooth/BluetoothDevice)). `BluetoothSocket.getMaxTransmitPacketSize()` (API 23) gives the SDU size to write ([BluetoothSocket](https://developer.android.com/reference/android/bluetooth/BluetoothSocket)).
- Interop: both implement Bluetooth Core LE Credit Based Flow Control; the secure Android variant requires an authenticated link key, so **use the insecure variant across ecosystems and encrypt at the app layer** unless you want a system pairing dialog. Google's Nearby Connections ships an Apple `ble_l2cap_socket.mm` and a shared `ble_l2cap_endpoint_channel` ([apple platform dir](https://github.com/google/nearby/tree/main/internal/platform/implementation/apple), [mediums](https://github.com/google/nearby/tree/main/connections/implementation/mediums)), which is the best available evidence that iOS CoC ↔ Android CoC is a real path — though Google's own iOS build table marks L2CAP "possible, not implemented" ([connections README](https://github.com/google/nearby/blob/main/connections/README.md)).
- Throughput: same radio; saves the ATT header and the notification-queue handshake. Apple has no published number; treat as "GATT, but closer to the ceiling."
- Library: none for React Native. Custom module.

### 3.3 Bluetooth Classic RFCOMM / SPP

- Android: `listenUsingRfcommWithServiceRecord` since API 5 ([BluetoothAdapter](https://developer.android.com/reference/android/bluetooth/BluetoothAdapter)). Would be the fastest Bluetooth option Android ↔ Android.
- iOS: Core Bluetooth's BR/EDR support is limited to what Apple exposes; arbitrary RFCOMM/SPP is reachable only through the **External Accessory** framework, which is for **MFi accessories** whose manufacturer whitelists your app's protocol ("The manufacturer of an MFi accessory decides which third-party apps may communicate with their accessories") ([External Accessory](https://developer.apple.com/documentation/externalaccessory)). An Android phone is not an MFi accessory. **Confirmed: not usable for phone-to-phone.** [react-native-bluetooth-classic](https://github.com/kenjdavidson/react-native-bluetooth-classic) (1.73.0-rc.17, 2025-11-19, 10 572/wk) documents exactly this split.

### 3.4 Wi-Fi Aware / NAN

**Android.** API 26+, feature-gated by `PackageManager.FEATURE_WIFI_AWARE`; data paths via `WifiAwareNetworkSpecifier` (API 29) + `ConnectivityManager.requestNetwork`; discovery messages ≤ ~255 bytes; permissions `NEARBY_WIFI_DEVICES` (API 33+, `neverForLocation`) or `ACCESS_FINE_LOCATION` (≤ 32) plus `ACCESS_WIFI_STATE`, `CHANGE_WIFI_STATE`, `CHANGE_NETWORK_STATE`, `INTERNET`; instant-communication mode on Android 13+ for 30 s ([Wi-Fi Aware guide](https://developer.android.com/develop/connectivity/wifi/wifi-aware), [WifiAwareNetworkSpecifier](https://developer.android.com/reference/android/net/wifi/aware/WifiAwareNetworkSpecifier)). Standards-based **NAN Pairing** arrived in API 34: `AwarePairingConfig`, valid only when `Characteristics.isAwarePairingSupported()` is true, with bootstrapping methods per Wi-Fi Aware 4.0 §9.5.21.7 including PIN, passphrase, QR and NFC ([AwarePairingConfig](https://developer.android.com/reference/android/net/wifi/aware/AwarePairingConfig), [Characteristics](https://developer.android.com/reference/android/net/wifi/aware/Characteristics)).

**iOS.** New in iOS 26 / iPadOS 26 (no macOS). "Your app can use the Wi-Fi Aware framework to connect with Wi-Fi Aware certified accessories"; works without infrastructure, cellular or internet; simultaneous with infrastructure Wi-Fi; usable in foreground and background; supported on **iPhone 12 and later**, iPad (10th gen)+, iPad Air (4th)+, iPad Pro 11" (3rd)+ / 12.9" (5th)+, iPad mini (6th)+ ([Wi-Fi Aware](https://developer.apple.com/documentation/wifiaware)). Requires the `com.apple.developer.wifi-aware` entitlement with `Publish` and/or `Subscribe` ([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.wifi-aware)) and a `WiFiAwareServices` Info.plist dictionary ([key](https://developer.apple.com/documentation/bundleresources/information-property-list/wifiawareservices)). Pairing is mandatory and goes through **DeviceDiscoveryUI** (`DevicePairingView` / `DevicePicker`, PIN shown in system UI) ([DeviceDiscoveryUI](https://developer.apple.com/documentation/devicediscoveryui)); data moves over Network framework `NetworkListener` / `NetworkConnection` with `.wifiAware` parameters ([WWDC25 session 228](https://developer.apple.com/videos/play/wwdc2025/228/)). Apple's Accessory Design Guidelines §56: "Peer devices and accessories integrating Wi-Fi Aware technology shall support the Wi-Fi Aware Specification – Version 4.0", "peer devices shall be Wi-Fi Aware certified" with secure pairing with NIK caching, multicast data protection, multicast management frame protection and beacon protection enabled; a peer device is explicitly "any third-party product (such as an accessory, embedded system, or **non-Apple phone/tablet**)" ([ADG PDF](https://developer.apple.com/accessories/Accessory-Design-Guidelines.pdf), §56.1–56.2). The framework exists because the EU DMA specification decision required "high-bandwidth peer-to-peer Wi-Fi connections", with Wi-Fi Aware 4.0 in iOS 26 and 5.0 due within nine months of that spec ([EC DMA developer portal](https://digital-markets-act.ec.europa.eu/developer-portal/interoperability/apple-specification-proceedings-interoperability-connected-devices-and-request-based-process_en)); Apple ships it worldwide, not EU-only.

**Does iPhone ↔ Android work?** Not demonstrated as of September 2026. Two Apple developer-forum threads collect the field evidence: iOS drops Android publish frames "missing DCEA attribute"; only the Galaxy S25 returned `isAwarePairingSupported() == true` (Pixel 9 and Xiaomi 14 did not); 6-digit PIN pairing failed with Qualcomm status 15; where pairing "succeeded" the subsequent data-path (NDP) request went unanswered. Apple DTS's position: read the ADG chapter, and "discuss these guidelines with your hardware and platform vendors" ([thread 790195](https://developer.apple.com/forums/thread/790195), [thread 801280](https://developer.apple.com/forums/thread/801280)). The only React Native wrapper, [react-native-wifi-aware 0.1.0](https://github.com/mahdidavoodi7/react-native-wifi-aware) (Nitro, iOS 26+ / Android 26+, Expo config plugin, published 2026-09-21, 1 star), says in its README: "Connecting an iPhone to an Android device is **not** a supported feature of this library", quarantines the attempt behind `initiatePairingWithForeignPeer` marked "experimental, expect failure", and notes QR-code pairing is unavailable on Apple platforms (PIN only) and that there is no Simulator support.

**Verdict.** Right standard, right bandwidth, wrong year. Watch it; do not build on it yet. Our own test hardware (Galaxy A16, a budget device) is unlikely to report `isAwarePairingSupported()`.

### 3.5 Wi-Fi Direct (P2P)

Android only: `WifiP2pManager` since API 14; `NEARBY_WIFI_DEVICES` (API 33+) or `ACCESS_FINE_LOCATION`; Location Mode must be on for discovery; the peer sees an **invitation dialog** ([Wi-Fi Direct guide](https://developer.android.com/develop/connectivity/wifi/wifi-direct)). iOS exposes no Wi-Fi Direct API; Apple's peer-to-peer Wi-Fi is AWDL, reached only through Multipeer Connectivity or Network framework `includePeerToPeer` between Apple devices ([includePeerToPeer](https://developer.apple.com/documentation/network/nwparameters/includepeertopeer)). Confirmed: **no cross-platform path.** [react-native-wifi-p2p 3.6.1](https://github.com/kirillzyusko/react-native-wifi-p2p) (2025-12-26, 531/wk, 26 open) is Android-only by design. Note the "legacy" mode of Wi-Fi Direct — Android creates a group and hands out its passphrase — is functionally the hotspot path in §3.10.

### 3.6 Apple Multipeer Connectivity and Google Nearby Connections

**Multipeer Connectivity** (iOS 7+) uses "infrastructure Wi-Fi networks, peer-to-peer Wi-Fi, and Bluetooth personal area networks"; requires `NSLocalNetworkUsageDescription` and `NSBonjourServices` ([Multipeer Connectivity](https://developer.apple.com/documentation/multipeerconnectivity)). Apple-to-Apple only; there is no Android implementation of its protocol. [react-native-multipeer-connectivity 0.1.0](https://github.com/XHMM/react-native-multipeer-connectivity) (2023-09-12, 147/wk, 11 stars) is the only wrapper and is dormant.

**Nearby Connections** is "a high level protocol on top of Bluetooth/Wi-Fi that acts as a medium-agnostic socket … the two devices share a list of all supported mediums and attempt to upgrade to the one with the highest bandwidth (eg. BT -> Wi-Fi)" ([connections README](https://github.com/google/nearby/blob/main/connections/README.md)). Strategies: `P2P_CLUSTER` (M-to-N, lower bandwidth), `P2P_STAR` (1-to-N), `P2P_POINT_TO_POINT` (1-to-1, highest throughput) ([strategies](https://developers.google.com/nearby/connections/strategies)). Android mediums per Google's table: Bluetooth Classic, BLE (GATT, L2CAP, extended advertising), Wi-Fi LAN, Wi-Fi Hotspot, Wi-Fi Direct, Wi-Fi Aware, WebRTC, NFC, USB. **iOS/macOS build: "The only medium supported is Wi-Fi LAN"**; BLE, Wi-Fi Hotspot, AWDL and WebRTC are listed as "possible, not implemented" ([connections README](https://github.com/google/nearby/blob/main/connections/README.md)). So an iPhone running Google's own Swift SDK can only meet an Android phone on a shared LAN — the exact thing client isolation blocks. Payloads: BYTES ≤ 32 KB, FILE any size, STREAM ([overview](https://developers.google.com/nearby/connections/overview)); Android permissions span `BLUETOOTH_SCAN/ADVERTISE/CONNECT`, `NEARBY_WIFI_DEVICES`, `ACCESS_FINE_LOCATION` (≤ 31) and `ACCESS_LOCAL_NETWORK` for API 37+ ([get started](https://developers.google.com/nearby/connections/android/get-started)); iOS needs `NSBluetoothAlwaysUsageDescription`, `NSLocalNetworkUsageDescription`, `NSBonjourServices` ([Swift get started](https://developers.google.com/nearby/connections/swift/get-started)). Requires Google Play services on Android. [expo-nearby-connections 1.1.1](https://github.com/puguhsudarma/expo-nearby-connections) (2026-08-20, Nitro, Expo 55 / RN 0.83, 314/wk) wraps Nearby on Android and **Multipeer on iOS** and states "Cross-platform P2P between Android and iOS is not supported." react-native-google-nearby-connection (0.0.9, 2018) is dead.

Confirmed: **no cross-platform bridge** between these two, and Nearby's iOS build does not help us.

### 3.7 Out-of-app channels: AirDrop, Quick Share, share sheet

- **AirDrop** works between "nearby Apple devices" with Wi-Fi and Bluetooth on and Personal Hotspot off ([Apple Support](https://support.apple.com/en-us/119857)). No Android sender/receiver from Apple.
- **Quick Share ↔ AirDrop** interoperability exists since November 2025 on the Pixel 10 family ([Google blog](https://blog.google/products/android/quick-share-airdrop/)), extended to Pixel 9 and named OEMs; Google's help page lists Pixel 8a or later plus "Certain Samsung, Oppo, OnePlus, Vivo, Xiaomi, Honor, Transsion, and Motorola devices", requires the iPhone's AirDrop set to **"Everyone for 10 minutes"**, and for unsupported devices falls back to a **QR code pointing at a cloud download** (internet on both sides, 24-hour retention on Google servers) ([Pixel Help](https://support.google.com/pixelphone/answer/9286773?hl=en)). Our Galaxy A16 is not on the list today.
- **Share sheet + file association.** Sending is trivial with `expo-sharing` (already a dependency). Receiving means registering a file type / URL scheme so "Open in native-rd" appears. This gives **one-way, best-effort, user-driven** transfer with the OS's own radios and no code of ours on the wire. Reliability is good when the pair is Apple↔Apple or Android↔Android; cross-platform it depends on Quick Share/AirDrop interop device lists or on internet. There is no return channel; the signed 2 KB response would be a second share in the opposite direction. **Viable as a manual fallback and for badge export** ([badge-export.md](./badge-export.md)); not a transport we can build the peer flow on.

### 3.8 Pairing-token exchange (~200 bytes)

- **QR code (recommended).** `expo-camera` ~56.0.8 is already installed; `CameraView` supports `onBarcodeScanned` with `barcodeScannerSettings: { barcodeTypes: ["qr"] }`; the config plugin sets `NSCameraUsageDescription` (default "Allow $(PRODUCT_NAME) to access your camera") and adds Android `CAMERA` ([expo-camera SDK 56](https://docs.expo.dev/versions/v56.0.0/sdk/camera/)). Standalone `expo-barcode-scanner` last published 13.0.1 on 2024-04-23 and is no longer in the SDK docs; barcode scanning lives in expo-camera ([npm](https://registry.npmjs.org/expo-barcode-scanner), [docs](https://docs.expo.dev/versions/latest/sdk/camera/)). 200 bytes fits comfortably in one QR (we can also add a BLE service UUID, an L2CAP PSM hint and a session key). Generation needs a QR renderer (e.g. `react-native-qrcode-svg`, not yet a dependency) — pure JS, no native code.
- **NFC.** iOS Core NFC (iOS 11) can **read** NDEF tags and, from iOS 13, **write** to tags ([Core NFC](https://developer.apple.com/documentation/corenfc), [writeNDEF](<https://developer.apple.com/documentation/corenfc/nfcndeftag/writendef(_:completionhandler:)>)); `NFCReaderUsageDescription` required. An iPhone cannot present itself as a tag except via `CardSession` (iOS 17.4, ISO 7816 APDU host-card emulation, **EEA-only** and limited to payments/keys/tickets categories) ([CardSession](https://developer.apple.com/documentation/corenfc/cardsession)). Android can emulate an ISO-DEP card via `HostApduService` (API 19, ~1 KB in ~300 ms recommended) ([HCE](https://developer.android.com/develop/connectivity/nfc/hce)), so **Android-as-tag, iPhone-as-reader** is possible in principle; the reverse is not. Android Beam (phone-to-phone NDEF push) was deprecated in Android 10 and its APIs removed in API 34 ([Android 10](https://developer.android.com/about/versions/10/behavior-changes-all), [API 34 diff](https://developer.android.com/sdk/api_diff/34/changes/android.nfc.NfcAdapter)). [react-native-nfc-manager 3.17.2](https://github.com/revtel/react-native-nfc-manager) (2025-11-28, 104 567/wk, 1 633 stars; v4.0.0-beta.9 for New Architecture, 2026-09-08; Expo plugin via `@expo/config-plugins` peer) covers reading/writing but HCE is a separate Android-only concern. Verdict: asymmetric and fiddly; QR is strictly better for us.
- **Ultrasonic.** [ggwave](https://github.com/ggerganov/ggwave) (MIT, 7 873 stars, last push 2026-04-16) moves 8–16 bytes/s over audible or 15 kHz "ultrasound" protocols with iOS Swift Package and Android/Java bindings but no React Native binding. 200 bytes ≈ 15–25 s of tone. No maintained RN library was found (`react-native-chirp` does not exist on npm; the Chirp SDK is no longer published). Not competitive with QR.

### 3.9 Internet fallback when both phones have cellular data

- **HyperDHT (Pear).** "Uses a series of holepunching techniques to make sure connectivity works on most networks"; default bootstrap nodes are public (`node1-3.hyperdht.org:49737`) and "You'll need at least one persistent node for the network to be completely operational" ([README](https://github.com/holepunchto/hyperdht/blob/main/README.md)). Relaying exists: `relayThrough` on server and client and `relayAddresses` "to hole-punch through when a direct connection cannot be established" ([docs.pears.com](https://docs.pears.com/building-blocks/hyperdht)). No published success rate for symmetric NAT / CGNAT. This is the transport our spike already runs on a phone ([react-native-bare-kit 0.15.5](https://github.com/holepunchto/react-native-bare-kit), 2026-09-17; hyperdht 6.34.0, 2026-09-03).
- **WebRTC data channels.** [react-native-webrtc 124.0.8](https://github.com/react-native-webrtc/react-native-webrtc) (2026-07-21, 183 721/wk, 4 994 stars, no `codegenConfig` so it rides the interop layer) supports `RTCDataChannel` on iOS/Android and has an Expo plugin ([@config-plugins/react-native-webrtc 15.0.2](https://github.com/expo/config-plugins), Expo ≥ 56). Needs a signaling channel (our QR token can carry an offer only if a rendezvous server relays the answer) and, per RFC 8656, "When a direct communication path cannot be found, it is necessary to use the services of an intermediate host that acts as a relay" — a TURN server ([RFC 8656](https://www.rfc-editor.org/rfc/rfc8656.html)).
- **libp2p.** js-libp2p's README lists Node.js and browser targets and no React Native support; not pursued.
- **Carrier NAT reality.** Mobile carriers put phones behind CGNAT in shared address space 100.64.0.0/10; RFC 6598 records that "some peer-to-peer applications cannot seed content due to the inability to open incoming ports through the CGN" ([RFC 6598](https://www.rfc-editor.org/rfc/rfc6598.html)). Two phones both on cellular are the hardest hole-punching case; **assume a relay is needed** and budget a small always-on node (HyperDHT bootstrap/relay or TURN). Once connected, throughput is bounded by the slower uplink — typically several Mbit/s, so 5 MiB in seconds. Internet fallback also re-introduces "data leaves the room", which the vision treats as a cost, not a feature.

### 3.10 Android local-only hotspot + iOS programmatic join (not in the original list; worth knowing)

- Android `WifiManager.startLocalOnlyHotspot()` (API 26): "Request a local only hotspot that an application can use to communicate between co-located devices … The network created by this method will not have Internet access"; the callback delivers a `SoftApConfiguration` with SSID, security type and credentials, and "Communicating this information is up to the application" (our QR/BLE token). Permissions: `CHANGE_WIFI_STATE` + `NEARBY_WIFI_DEVICES` (API 33+) or `ACCESS_FINE_LOCATION` (≤ 32). It fails if the user is already tethering ([WifiManager](https://developer.android.com/reference/android/net/wifi/WifiManager)).
- iOS `NEHotspotConfigurationManager.apply(_:)` (iOS 11): "the device prompts the user for approval. Without explicit user consent, your app can't make configuration changes"; needs the `com.apple.developer.networking.HotspotConfiguration` entitlement; configurations are removed on uninstall ([NEHotspotConfigurationManager](https://developer.apple.com/documentation/networkextension/nehotspotconfigurationmanager), [entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.hotspotconfiguration)).
- This is what Google's Nearby Connections does for its Android `WIFI_HOTSPOT` medium, and the Apple platform code in google/nearby contains a `wifi_hotspot.mm` that joins by SSID/password ([source](https://github.com/google/nearby/blob/main/internal/platform/implementation/apple/wifi_hotspot.mm)), even though Google's iOS build does not enable it.
- Costs: the iPhone drops its infrastructure Wi-Fi for the session (iOS may warn "No Internet Connection"); one system prompt on iOS; Android needs location-class permission; role is fixed (Android hosts). Benefit: Wi-Fi throughput, so the media transfer is seconds, and — importantly — **our existing HyperDHT/Bare transport would work unchanged on that link** if the Android phone also runs the local DHT nodes, exactly as the spike already configures it. No React Native library covers this; the native surface is two functions per platform.
- Uncertainty: not tested by us; iOS behaviour when the joined network has no internet (auto-fallback to cellular for the socket is not an issue since we bind to the hotspot's local address, but system UI may nag).

## 4. Time to move 5 MiB (41.9 Mbit)

| Path                                              | Rate basis                            | 5 MiB           |
| ------------------------------------------------- | ------------------------------------- | --------------- |
| BLE, legacy 27-byte packets, 1M PHY (SIG ceiling) | 0.39 Mbit/s                           | ~108 s          |
| BLE, DLE 251-byte, 1M PHY (SIG ceiling)           | 0.80 Mbit/s                           | ~52 s           |
| BLE, DLE 251-byte, 2M PHY (SIG ceiling)           | 1.43 Mbit/s                           | ~29 s           |
| BLE, **planning assumption for real phones**      | 0.15–0.8 Mbit/s                       | **~1–5 min**    |
| Android local-only hotspot / Wi-Fi Aware          | ≥ 20 Mbit/s (Wi-Fi class; unmeasured) | ≤ 2–3 s         |
| Internet via relay, both on cellular              | 5–20 Mbit/s uplink (varies)           | 2–8 s + connect |

The 200-byte token and the 2 KB signed return are negligible on every path.

## 5. Ranked recommendation

1. **Primary, infrastructure-free, cross-platform: BLE.** QR code carries `{sessionKey, serviceUUID, role hint}`; the hosting phone runs a GATT server (peripheral) and advertises; the joining phone connects as central, negotiates MTU, reads a PSM characteristic and opens an insecure L2CAP CoC if both sides expose one, else streams over write-without-response / notifications with app-level ACKs and resume offsets. App-layer encryption with the existing P-256 device keys; no system pairing dialog. Accept 1–5 minutes for 5 MiB with a visible progress bar and a "keep both phones unlocked and this screen open" instruction (iOS backgrounded advertising is invisible to Android). Needs a small Nitro module for the peripheral role (nothing maintained exists); `react-native-ble-manager` 12.x can serve the central role on the New Architecture.
2. **Opportunistic upgrade: Android local-only hotspot + iOS join.** After BLE pairing, if the Android side is the host (or can be made the host), start a local-only hotspot, send SSID/passphrase over the BLE channel, and let iOS join after its one system prompt; then run the existing Bare/HyperDHT transport (or plain TCP) over that link. Falls back to BLE if the user declines. Turns minutes into seconds for the media.
3. **Fallback with internet: HyperDHT with a self-hosted bootstrap/relay node**, which the spike already builds; or WebRTC + TURN if Bare proves too heavy. Assume CGNAT means a relay is used, and say so in the UI ("sending via Rollercoaster relay").
4. **Manual fallback: share sheet.** Export the evidence bundle as a file via `expo-sharing`; register a file type so the receiving app can import; return the signed response the same way. Works today; not automatic; cross-platform only where the OSes interoperate (Pixel/AirDrop) or via cloud.
5. **Watch, don't build: Wi-Fi Aware.** Re-evaluate when (a) Android mid-range devices report `isAwarePairingSupported()`, (b) any public report shows iPhone ↔ Android NDP working, or (c) Apple documents a QR/programmatic pairing route. react-native-wifi-aware is a reasonable wrapper to test against when that day comes.

**What is uncertain**

- Real iPhone ↔ Galaxy A16 BLE throughput. Unmeasured; could be as low as ~100 kbit/s if the controllers settle on long connection intervals and small MTUs. This is the single number that decides whether BLE-only is acceptable UX.
- Whether Android L2CAP CoC (insecure) interoperates cleanly with iOS `CBL2CAPChannel` on our specific devices. Google's source suggests yes; nothing public proves it for these models.
- iOS behaviour on a joined hotspot without internet, and whether the Bare runtime binds correctly to the hotspot interface.
- Wi-Fi Aware cross-ecosystem pairing — unknown timeline.
- HyperDHT hole-punch success rate between two cellular phones without a relay — no published figure.

## 6. What this means for the peer-evidence spike

- The spike's transport layer (Bare + HyperDHT with three local DHT nodes) is **not wasted**: it is the right thing to run once any IP link exists — Android local-only hotspot (§3.10), a permissive LAN, or the internet fallback. What it cannot do is create the link. The blocker on 2026-09-21 was the radio/network layer, not Pear.
- **Don't retest the current spike on more Wi-Fi networks** hoping for a permissive one; schools and cafés will keep isolating clients. Instead add a link-creation step before the DHT step.
- **Next spike (proposed, in order):**
  1. BLE peripheral + central across the iPhone 17 Pro and Galaxy A16, stock GATT, measure MTU negotiated, PHY, and bytes/second for a 5 MiB stream in both directions. Then add insecure L2CAP CoC and measure again. Record `maximumWriteValueLength`, `onMtuChanged`, `onPhyUpdate`.
  2. Android `startLocalOnlyHotspot` → QR/BLE → iOS `NEHotspotConfiguration` join → run the **existing spike backend** over that link with WAN disabled. This is the fastest route to "evidence received, endorsement returned" on real phones.
  3. Only if (1) and (2) both fail: internet fallback via a self-hosted HyperDHT bootstrap node, both phones on cellular, measuring connect time and whether the relay is used.
- Keep the spike's separation intact: transport selection is independent of OB3 verification, on-device endorsement signing and validator conformance ([Pear evaluation §TL;DR](./pear-p2p-evaluation.md)).
- Pairing UX for the vision's "learner and invited peer meet physically" flow should be **QR on screen, camera on the other phone**; it is the only pairing channel that is symmetric across iOS and Android without special hardware support.
